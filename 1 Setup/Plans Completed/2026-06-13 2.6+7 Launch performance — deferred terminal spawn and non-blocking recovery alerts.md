## Purpose
Eliminate two unnecessary costs that slow every cold launch: an eager Zsh PTY spawn that runs
the user's shell config before the window is visible (ISS-107), and blocking modal recovery
dialogs that hold the main thread until the user dismisses them one by one (ISS-108).

## Success Condition
- `swift build` clean across all packages — no new warnings in module 7 or 2.6.
- Cold launch (Xcode Profile → Time Profiler): no `Process.run()` / `posix_openpt` call
  appears before the first frame renders — PTY spawn is absent from the critical path.
- Opening Sputnik with one crash-recovery file present: the main window is immediately
  interactive; a non-blocking notification appears in the status bar (or as a SwiftUI
  `.alert`), not a blocking modal.
- Opening the terminal strip for the first time after launch spawns the shell as before
  (one tab, correct working directory, profile applied).
- Relaunching with no recovery files: no observable change in behaviour.

## Steps

### 1. Gate `addTab()` behind a visibility/demand flag (ISS-107)

**File:** `7 Terminal/TerminalView.swift`

**What:** Add a `@State private var hasLaunched = false` flag to `TerminalView`. Replace the
current unconditional `onAppear` call:

```swift
// Before
.onAppear {
    if tabs.isEmpty {
        addTab()
    }
}
```

with a conditional that defers spawn until the terminal strip is actually shown:

```swift
// After
.onAppear {
    guard !hasLaunched else { return }
    hasLaunched = true
    if tabs.isEmpty {
        addTab()
    }
}
```

Then check whether the terminal strip's visibility is wired through
`windowState.layout.terminalVisible`. If `TerminalView` is only added to the hierarchy when
the terminal is visible (confirm in `ContentView`), the `onAppear` guard is sufficient.
If `TerminalView` is always in the hierarchy but hidden, additionally wrap `addTab()` behind:

```swift
.onAppear {
    guard !hasLaunched, windowState.layout.terminalVisible else { return }
    hasLaunched = true
    addTab()
}
// And trigger on first show if not yet launched:
.onChange(of: windowState.layout.terminalVisible) { _, isVisible in
    guard isVisible, !hasLaunched else { return }
    hasLaunched = true
    addTab()
}
```

**Why:** `TerminalView.onAppear` currently fires as part of the first `ContentView` render,
before the user sees the window. Forking a Zsh process and running `~/.zshrc` adds
measurable cold-start time (ISS-107). The fix defers the fork to first actual use with
zero behaviour change for users who open the terminal immediately.

---

### 2. Audit `ContentView` to confirm terminal strip visibility wiring (ISS-107)

**File:** `App-Sputnik/ContentView.swift`

**What:** Check whether `TerminalView()` is rendered unconditionally or conditionally on
`windowState.layout.terminalVisible`. If it is always rendered, confirm the `.onChange`
approach from Step 1 is in place. If there is already a conditional guard (e.g. `if
terminalVisible { TerminalView() }`), then the `onAppear` guard alone is enough and no
`.onChange` is needed.

Document the finding with a comment in `ContentView` near the terminal strip so future
maintainers understand the deferred-spawn contract.

**Why:** The correct deferral strategy depends on whether `TerminalView` is in the hierarchy
at all times or only when visible. Reading the code before writing the fix prevents
introducing a redundant or wrong condition (SR-2).

---

### 3. Move recovery-file presentation out of `AppDelegate` (ISS-108)

**File:** `2 Foundation/2.6 App Lifecycle/AppDelegate.swift`

**What:** Remove the `for name in pendingNames { presentAlert(alert) }` loop from
`applicationDidFinishLaunching`. Instead, store the pending names on `AppState`:

```swift
// AppDelegate.applicationDidFinishLaunching — replace the loop with:
if !pendingNames.isEmpty {
    appState?.pendingRecoveryNames = pendingNames
}
```

**Why:** `NSAlert.runModal()` is a synchronous blocking call on the main thread. Calling it
inside a `Task` continuation — even though the continuation is async — still runs `runModal`
synchronously when the continuation body executes on `@MainActor`. Multiple files mean
multiple serial blocks before the window is interactive (ISS-108). Moving the list to
`AppState` lets the UI present it non-blockingly.

---

### 4. Add `pendingRecoveryNames` to `AppState` (ISS-108)

**File:** `2 Foundation/2.2 Global State Management/AppState.swift`

**What:** Add a new `@Observable`-tracked property:

```swift
/// Names of crash-recovery files awaiting user action. Set at launch by AppDelegate;
/// cleared when the user accepts or dismisses each entry.
public var pendingRecoveryNames: [String] = []
```

Add a mutating helper used by the UI:

```swift
/// Removes a single recovery entry after the user accepts or discards it.
public func clearRecovery(name: String) {
    pendingRecoveryNames.removeAll { $0 == name }
}
```

**Why:** `AppState` is the single source of truth for shared, cross-module UI state (SR-1,
2.2 module invariant). Placing `pendingRecoveryNames` here lets any view observe it without
creating a new channel.

---

### 5. Present recovery notifications non-blockingly in `ContentView` (ISS-108)

**File:** `App-Sputnik/ContentView.swift`

**What:** Add a SwiftUI `.alert` modifier (or toolbar badge) driven by
`appState.pendingRecoveryNames`. A single alert listing all affected files is less disruptive
than one per file:

```swift
// At the end of ContentView.body modifiers:
.alert(
    "Unsaved Changes Recovered",
    isPresented: Binding(
        get: { !appState.pendingRecoveryNames.isEmpty },
        set: { if !$0 { appState.pendingRecoveryNames = [] } }
    )
) {
    Button("Review") { /* future: open recovered files */ }
    Button("Dismiss", role: .cancel) {
        appState.pendingRecoveryNames = []
    }
} message: {
    let names = appState.pendingRecoveryNames.joined(separator: "\n")
    Text("The following files have unsaved changes from a previous session:\n\(names)")
}
```

The alert appears after the first frame renders — the user sees the window immediately and
can interact with it. Dismissing the alert clears `pendingRecoveryNames`.

**Why:** SwiftUI `.alert` is presented by the system after the view renders its first frame,
making it non-blocking by design. It does not call `runModal` and does not hold the main
thread (ISS-108, SR-4).

---

### 6. Remove `presentAlert` from `AppDelegate` (ISS-108)

**File:** `2 Foundation/2.6 App Lifecycle/AppDelegate.swift`

**What:** Delete the `private func presentAlert(_ alert: SputnikAlert)` helper and its
recovery-alert call site. Verify no other callers remain.

**Why:** After Step 3, `presentAlert` is dead code. Removing it keeps the file clean (SR-6)
and prevents a future author from accidentally re-adding a blocking modal.

## Risks and Constraints

- **MR-3 / SW-1:** PTY spawn uses `Foundation.Process` which must run on `@MainActor`
  (already the case via `Task { await manager.startSession(...) }`). The deferral does not
  change the actor; it only delays when the call is made.
- **SR-2:** Recovery data must not be lost. The alert must appear before the user can
  accidentally overwrite the recovered file. SwiftUI `.alert` fires on the first render
  cycle, which satisfies this constraint — but verify it fires before any
  `onChange(activeDocumentID)` triggered auto-save.
- **Terminal behaviour unchanged:** Users who always open the terminal will see no change.
  Users who never open it save the PTY startup cost entirely.
- **ISS-101/102 (existing plans):** Those plans fix phantom recovery files on the *write*
  side. This plan fixes the *presentation* side. They are complementary and can land in
  either order.
- **Foundation change (Step 4):** Adding a field to `AppState` is a Foundation-module touch
  — flag per skill rule: test that existing `AppState`-dependent views compile and no new
  warnings appear.

## Purpose

Add the Interaction feature: when the user's selection is inside a **special element** (a recognised structural construct), an "Interact with" action (Edit menu ⌘I, right-click, keyboard shortcut) auto-inserts the Resource content that element requires into the designated spots — e.g., a "Sentence parser" table gains a Lexical row and a Structural row populated from the Grammar Resource.

A special element is recognised from **two combined signals**: a **syntax term** (the structural pattern, e.g. a `| … |` table) *and* a **contextual clue** (the nearest heading above the selection, e.g. "Sentence parser"). Both signals are matched against a **special-element registry** — a per-resource declarative list (`special_elements.json`) where each entry names an element, its trigger terms, and its **slots** (each slot marked `userContent` or `resource`, with the resource lookup that fills it). When a registered element is detected on a right-clicked selection, **Interaction replaces More-Context** in the menu; choosing it **auto-fills every resource slot** with the top resource match for the selection, inserting the full templated structure. A syntax term with no matching registry entry falls back to fuzzy heading matching (a single best section), and unmatched selections keep showing More-Context.

## Success Condition

- A selection is recognised as a special element when a syntax term (structural pattern) fires; the contextual heading and selected text are matched against the **registry** to resolve a `SpecialElementDefinition`. The Edit ▸ "Interact with" item (⌘I) and the right-click item are enabled only when an element is recognised, and disabled otherwise.
- **Precedence:** when a special element is detected on a right-clicked selection (and Interaction is enabled for that language), the context menu shows the "Interact with…" item **instead of** the "More Context: …" items. When no special element is detected (or Interaction is disabled), the More-Context items appear exactly as today. The two never appear together.
- **Registry-driven, auto-fill:** choosing a registered element (e.g. "Sentence parser") inserts its full template at once — `userContent` slots left for the user, every `resource` slot populated with the top resource lookup for the selection. A resource slot with several strong candidates opens a submenu to choose; otherwise it fills silently.
- The registry routes by both signals: a Markdown table under a "Sentence parser" heading resolves to the grammar `sentence-parser` definition (Lexical + Structural rows from Grammar Help); the same table under no registered heading resolves to a generic Markdown-table definition (or fuzzy fallback). Grammar slot lookups reuse `GrammarHelpIndex.searchByTerm(_:preferStructural:)` from ISS-135.
- Help ▸ Interaction submenu (mirroring More-Context) shows per-language toggles (Markdown, HTML, ASCII Art, JSON, Grammar, All On); disabling a language suppresses detection for that mode.
- Toggling a language off in Help ▸ Interaction persists across app launches.
- No existing feature (More-Context, auto-complete, grammar check) regresses.
- Swift Testing coverage for: registry load + decode; trigger resolution (syntax term + heading → definition; "Sentence parser" → grammar `sentence-parser`); auto-fill of resource slots from the index; fuzzy fallback when no registry entry matches; More-Context vs Interaction precedence; multi-slot template insertion format; menu enable/disable logic; toggle persistence.

## Step 3 — Define `SpecialElement` and `SpecialElementKind` in Foundation (2.7)

**File:** `2 Foundation/2.7 Utilities/SpecialElement.swift` (new)

What:
- `SpecialElementKind`: `String`, `Codable`, `Sendable` enum with cases: `markdownTableRow`, `htmlTableRow`, `asciiTableRow`, `markdownBlockquote`, `htmlListItem`, `fencedCodeBlock`, `htmlCodeBlock`, `asciiBoxRegion`.
- `SpecialElement`: `Sendable` struct —
  - `kind: SpecialElementKind` — the **container** shape (how/where to insert: table row, blockquote, …)
  - `definitionID: String?` — the resolved registry entry id (e.g. `"sentence-parser"`), or `nil` when only a syntax term matched (generic → fuzzy fallback). This is the **semantic** identity, orthogonal to `kind`.
  - `syntaxTerm: String` — the structural signal that fired (e.g. `"table"`, `"blockquote"`, `"code block"`); matched against registry `triggers.syntaxTerms`.
  - `contextHeading: String?` — the nearest heading text above the selection (e.g. `"Sentence parser"`), or `nil` if none found; matched against registry `triggers.headingCues`.
  - `elementRange: NSRange` (the whole element)
  - `selectedLineRange: NSRange` (the line the selection is on)
  - `insertionRange: NSRange` (where content goes)
  - `insertionPrefix: String` (formatting prefix for inserted text, e.g. `"| "` for a table row)

Why: Foundation owns the data shape (SR-1). `kind` = insertion mechanics; `definitionID` = content schema — keeping them separate lets one container (`markdownTableRow`) host many semantic elements (`sentence-parser`, `glossary`, …). Module 9.8 creates these; modules 3/4/8 pass them back via `InteractionQuery`.

## Step 3b — Define the special-element registry (Foundation 2.7 types + module-9 data)

**Files:** `2 Foundation/2.7 Utilities/SpecialElementDefinition.swift` (new types) and `9 Resources/9.8 Interaction/special_elements.json` (new data, bundled).

What — Foundation owns the shape (SR-1), module 9 owns the data:
- `SpecialElementDefinition`: `Codable, Sendable` — `id: String`, `displayName: String`, `resourceLanguage: WritingAssistLanguage`, `container: SpecialElementKind`, `triggers: ElementTriggers`, `slots: [ElementSlot]`.
- `ElementTriggers`: `Codable, Sendable` — `syntaxTerms: [String]`, `headingCues: [String]`.
- `ElementSlot`: `Codable, Sendable` — `role: String`, `label: String`, `source: SlotSource`.
- `SlotSource`: `Codable, Sendable` enum — `.userContent` | `.resource(lookup: ResourceLookup)`.
- `ResourceLookup`: `String, Codable, Sendable` enum — the named lookup that fills a resource slot, each mapping to an existing index call:
  - `.lexicalDefinition` → `GrammarHelpIndex.searchByTerm(selection, preferStructural: false)`
  - `.structuralAnalysis` → `GrammarHelpIndex.searchByTerm(selection, preferStructural: true)` (+ `GrammarSelectionAnalyzer`)
  - `.markdownTopic` / `.htmlTopic` / `.asciiTopic` → the respective index `search(selection)` best match
- `special_elements.json`: the authored registry. Seed entries: the grammar `sentence-parser` (container `markdownTableRow`; slots: `sentence`=userContent, `lexical`=resource(.lexicalDefinition), `structural`=resource(.structuralAnalysis)); plus generic per-container fallbacks for Markdown/HTML/ASCII tables, blockquotes, lists, and code blocks. Decode is defaulted/tolerant — an unknown `lookup` or `source` degrades to skipping that slot, never a crash (SR-2).

Why: this is the user-requested "special element list." It makes Interaction's behaviour declarative and data-extensible: adding a new element type is a JSON entry, not new Swift. Reusing the ISS-135 `searchByTerm(_:preferStructural:)` primitives for the grammar slots means no new lookup code for the headline case.

## Step 4 — Build `SpecialElementDetector` in 9.8

**File:** `9 Resources/Sources/9.8 Interaction/SpecialElementDetector.swift` (new)

What: `@MainActor` class `SpecialElementDetector: SpecialElementDetecting`. Method: `detect(in text: String, selectedRange: NSRange, mode: EditorMode) -> SpecialElement?`.

Detection is **two-signal** — a candidate is only returned when a **syntax term** matches; the **contextual heading** is then captured (and refines, never suppresses, the result). Both ride on the returned `SpecialElement`.

**Signal 1 — syntax term** (structural pattern on/around the selected line), per mode:
- **Markdown / TXT-with-MD**: line matches `^\s*\|.+\|` → `markdownTableRow` (`syntaxTerm = "table"`); `^\s*>` → `markdownBlockquote` (`"blockquote"`); inside a ` ``` `…` ``` ` span → `fencedCodeBlock` (`"code block"`).
- **HTML**: innermost enclosing tag at `cursorOffset` — `<tr>` → `htmlTableRow` (`"table"`); `<li>` → `htmlListItem` (`"list"`); `<pre>` → `htmlCodeBlock` (`"code block"`).
- **ASCII**: selected line has `|` and an adjacent line also has `|` → `asciiTableRow` (`"table"`); enclosed by box-drawing chars (`─`, `│`, `╔`, …) → `asciiBoxRegion` (`"box"`).
- **JSON**: returns `nil` for now (toggle exists for future use; documented in guide).

**Signal 2 — contextual heading** (`findContextHeading`): from the selected line, scan **upward** for the nearest heading and capture its text into `contextHeading`:
- Markdown/TXT: nearest preceding `^#{1,6}\s+(.*)$` line.
- HTML: nearest preceding `<h1>`–`<h6>` element's inner text.
- ASCII: nearest preceding non-empty line that is centred/underlined or all-caps (a title row heuristic).
- `contextHeading = nil` when none is found above the element.

**Resolve the registry definition** (`SpecialElementRegistry.resolve`, Step 5a): match the two signals against `special_elements.json`:
- A definition matches when its `triggers.syntaxTerms` contains `syntaxTerm` AND (its `triggers.headingCues` is empty OR fuzzily matches `contextHeading`). Heading-cued definitions (e.g. `sentence-parser`) outrank generic container-only definitions (e.g. a bare `markdownTableRow`), so "table under *Sentence parser*" resolves to grammar, while a bare table resolves to the generic Markdown-table entry.
- Set `definitionID` to the winning entry's id. If a generic container definition exists, detection always succeeds (with `definitionID` = that generic entry); if neither a specific nor a generic entry matches, `definitionID = nil` → the provider uses fuzzy fallback (Step 5b/5c).

- All detection is pure string/regex — no `NLTagger` here; run synchronously in the actor over the visible range only (SR-4).

`insertionRange` calculation per kind:
- `markdownTableRow`, `htmlTableRow`, `asciiTableRow`: end of the line + 1 (start of next line), inserting a full new row.
- `markdownBlockquote`: end of the last `>` line in the contiguous block.
- `htmlListItem`: after the closing `</li>`.
- `fencedCodeBlock`, `htmlCodeBlock`: after the closing fence/tag.
- `asciiBoxRegion`: last line before the closing border.

Why: detection is isolated and testable; `@MainActor` because it reads from `NSTextView.selectedRange` at the call site. Resolving the registry here (not in the provider) means the host's precedence check (Step 8b) and the provider both work off a single `detect` call that already knows the element's identity.

## Step 5b — Build `InteractionProvider` in 9.8 (registry-driven, auto-fill)

**File:** `9 Resources/Sources/9.8 Interaction/InteractionProvider.swift` (new)

What: `actor InteractionProvider: InteractionProviding`, holding the `SpecialElementRegistry`, the resource indexes, and (for fallback) a `ResourceSectionIndex` + `HeadingFuzzyMatcher`.

Method `sections(for query: InteractionQuery) async -> InteractionResult`:

**Primary path — registered element (`query.detectedElement.definitionID != nil`):**
1. Fetch the `SpecialElementDefinition` from the registry.
2. Walk its `slots` in order. For each:
   - `.userContent` slot → emit a placeholder `InteractionSectionItem` (label only, empty content) so the inserted template shows the row but leaves it for the user.
   - `.resource(lookup:)` slot → run the named `ResourceLookup` against the definition's `resourceLanguage` index, keyed by `query.selectedText` (the sentence/word). Grammar lookups reuse `GrammarHelpIndex.searchByTerm(_:preferStructural:)` (ISS-135). Take the top match → `content`; if ≥2 matches clear a confidence gap, attach the alternates so the popup can offer a per-slot submenu (the only place the user picks; default is auto-fill of the top match).
3. Return an ordered `InteractionResult` whose `sections` ARE the slots (one item per slot, in template order), with `insertionDescription` = `definition.displayName`.

**Fallback path — generic element (`definitionID == nil`):** the earlier heading-fuzzy behaviour — pick candidate language from `kind`, build a weighted query (`contextHeading` + `syntaxTerm` + `selectedText`), fuzzy-match `ResourceSectionIndex` headings via `HeadingFuzzyMatcher`, return up to 8 ranked single-section candidates for the user to pick one.

If a resource slot yields nothing (or the fallback clears nothing), that slot/section is omitted; an all-empty result makes Step 8 show "No relevant sections found" (no crash, SR-2).

Why: the registry path makes the headline case deterministic and multi-slot — "Sentence parser" inserts a Lexical row and a Structural row, each filled by the existing scored grammar lookup. The fuzzy path is retained only for elements not (yet) in the registry, so nothing regresses for unlisted constructs.

## Step 5c — Build `ResourceSectionIndex` + `HeadingFuzzyMatcher` in 9.8 (fallback infra)

**Files:** `9 Resources/Sources/9.8 Interaction/ResourceSectionIndex.swift`, `…/HeadingFuzzyMatcher.swift` (new)

These support the **fallback path** only (registered elements never touch them):
- `ResourceSectionIndex` (`actor`) + `ResourceSection` (`topicID`, `heading`, `sectionBody`, `resourceLanguage`): flattens each topic into sections keyed by heading — the topic title plus each `##`/`###` body sub-heading (verified populated: grammar 49/50, markdown 11/11). HTML/ASCII topics fall back to title + `searchTerms`. Cached per language for app lifetime (SR-3).
- `HeadingFuzzyMatcher`: `static func score(query:heading:) -> Double` — deterministic, dependency-free blend of token overlap (Jaccard), ordered substring containment, and a light Levenshtein ratio (tolerant of typos like "parsr" → "parser"). Returns 0–1; trivially unit-testable.

Note: `LocalSemanticSearch` (Foundation 2.7, NLEmbedding) exists but loads a ~300 MB model on first use — too heavy for an inline popup (SR-3/SR-4). The user asked for "fuzzy logic"; this lightweight matcher is the default, with `LocalSemanticSearch` noted as an opt-in future enhancement.

Why: keeps the fallback ranker isolated and testable; avoids a 300 MB model in a context-menu interaction.

## Step 6 — Build `ContentInserter` in 9.8

**File:** `9 Resources/Sources/9.8 Interaction/ContentInserter.swift` (new)

What: `@MainActor` class `ContentInserter: InteractionInserting`.

Two entry points:
- `insertTemplate(_ result: InteractionResult, into element: SpecialElement, fullText: String) -> (newText: String, insertionRange: NSRange)` — **the registry/auto-fill path.** Formats *every* slot/section in `result.sections` into the container shape of `element.kind` and inserts them as a contiguous block at `element.insertionRange`. For `sentence-parser` that's two new table rows (Lexical, Structural); `userContent` placeholder slots insert as an empty row of the same shape.
- `insert(_ item: InteractionSectionItem, into element: SpecialElement, fullText: String) -> …` — **the fuzzy-fallback path,** inserting the single chosen section.

Per-container formatting (shared by both):
- `markdownTableRow` / `asciiTableRow`: each slot becomes `| <label> | <content> |`, matching the element's column count.
- `htmlTableRow`: `<tr><td>…</td></tr>` per slot.
- `markdownBlockquote`: prepend `> ` to each content line.
- `htmlListItem`: `<li>…</li>`.
- `fencedCodeBlock` / `htmlCodeBlock`: new fenced block / `<pre><code>` after the existing one.
- `asciiBoxRegion`: indent to the box's interior padding.

Returns the full new text plus the `NSRange` of the inserted block (so the host can select it). The host calls `NSTextView.insertText(_:replacementRange:)` — never direct string mutation (SR-2, undo-safe).

Why: formatting is isolated from lookup and UI; the template entry point is what realises the user's "auto-fill all slots" choice; `@MainActor` because it produces text the host writes to `NSTextView`.

## Step 7 — Build `InteractionCoordinator` in 9.8

**File:** `9 Resources/Sources/9.8 Interaction/InteractionCoordinator.swift` (new)

What: `@MainActor` class `InteractionCoordinator`.

Properties:
- `private let provider: InteractionProvider`
- `private let inserter: ContentInserter`
- `private weak var settingsStore: SettingsStore?`
- `private(set) var detectedElement: SpecialElement?`
- `private(set) var isAvailable: Bool = false`

Methods:
- `updateDetection(text: String, selectedRange: NSRange, mode: EditorMode)` — called on selection change; runs `SpecialElementDetector.detect` (which resolves the registry); sets `detectedElement` and `isAvailable`; checks `WritingAssistMatrix.interaction` toggle for `mode`'s language before detecting.
- `trigger(relativeTo rect: NSRect, in view: NSView, selectedText: String, fullText: String, mode: EditorMode, onInsert: @escaping (String, NSRange) -> Void)` — builds `InteractionQuery` from `detectedElement`, calls `provider.sections(for:)` async, then branches on the result:
  - **Registered element (auto-fill):** call `inserter.insertTemplate(result, into: element, fullText:)` and hand the `(newText, range)` to `onInsert` immediately — no pick step. Exception: any slot carrying alternates (Step 5b) first shows a small per-slot submenu via `InteractionPopupMenu`; the chosen alternate replaces that slot's content before the template is built.
  - **Fuzzy fallback:** present `InteractionPopupMenu` of ranked sections; on pick, call `inserter.insert(item, …)` → `onInsert`.
- `interactionLanguage(for mode: EditorMode) -> WritingAssistLanguage?` — maps `EditorMode` to `WritingAssistLanguage` for toggle check; returns `nil` for unsupported modes.

Why: the coordinator is the single orchestration point; the auto-fill branch realises the user's "fill all slots at once" choice, while a slot with genuine ambiguity still offers a choice. Host modules (3, 4, 8) hold a reference to one shared coordinator (vended from Foundation or created per-panel, TBD in wiring step).

## Step 8b — Add the `SelectionContextMenu` precedence helper (Foundation 2.7)

**File:** `2 Foundation/2.7 Utilities/SelectionContextMenu.swift` (new)

What: a single `@MainActor enum SelectionContextMenu` that encodes the **Interaction-replaces-More-Context** rule in one place, so all three hosts behave identically (SR-1). It supersedes direct `MoreContextMenu.items(...)` calls in the hosts.

```swift
static func items(
    forSelectedText selectedText: String,
    fullText: String,
    cursorOffset: Int,
    selectionLength: Int,
    mode: EditorMode,
    detector: SpecialElementDetecting,        // module-9 concrete, via protocol
    interactionEnabled: Bool,                  // WritingAssistMatrix.interaction for this mode's language
    moreContextKinds: [HelpTopic],
    resolver: HelpContextResolving,
    onInteract: @escaping (SpecialElement) -> Void,
    onMoreContext: @escaping (HelpRequest?) -> Void
) -> [NSMenuItem]
```

Logic:
1. If `selectedText` is blank → return `[]`.
2. Run `detector.detect(in:selectedRange:mode:)`. If it returns a `SpecialElement` **and** `interactionEnabled` → return a single "Interact with…" `ClosureMenuItem` whose action calls `onInteract(element)`; **do not** add any More-Context items.
3. Otherwise → return the existing `MoreContextMenu.items(...)` result unchanged.

Why: the user requires that a detected special element shows Interaction *instead of* More-Context. Centralising the branch in Foundation means the editor, Markdown preview, and HTML preview can't drift; each host just calls `SelectionContextMenu.items(...)` and inserts the result. `MoreContextMenu` stays as-is and is reused internally.

## Step 15 — Write Swift Testing coverage

**File:** `9 Resources/Tests/InteractionTests.swift` (new)

Tests to cover:
- `SpecialElementRegistry`: `special_elements.json` loads and decodes; a malformed entry is skipped without failing the rest; `resolve(syntaxTerm:contextHeading:)` returns the `sentence-parser` definition for `("table", "Sentence parser")`, a generic Markdown-table definition for `("table", nil)`, and `nil` for an unknown syntax term; heading-cued entries outrank generic ones.
- `SpecialElementDetector`: each container kind detected from known strings (Signal 1); `contextHeading` captured from the nearest heading above (Signal 2), `nil` when none precedes; `definitionID` set from the registry; `nil` element for unsupported text.
- `InteractionProvider` (headline case, auto-fill): the `sentence-parser` definition yields one section per slot in template order — a `userContent` placeholder for `sentence`, a Lexical section from `searchByTerm(_:preferStructural:false)`, a Structural section from `searchByTerm(_:preferStructural:true)`; a resource slot with no match is omitted, not crashed.
- Fuzzy fallback (`definitionID == nil`): `ResourceSectionIndex` flattens a grammar topic into one `ResourceSection` per `##`/`###` heading (and HTML topics into a single title section); `HeadingFuzzyMatcher` scores exact > typo ("parsr"→"parser") > unrelated; the provider returns ranked single-section candidates.
- **Precedence:** `SelectionContextMenu.items(...)` returns a single "Interact with…" item (no More-Context items) when the detector resolves an element and Interaction is enabled; returns the More-Context items when the detector returns `nil`; returns More-Context items when Interaction is disabled even though an element exists.
- `ContentInserter.insertTemplate`: the `sentence-parser` result inserts two new table rows (Lexical, Structural) plus the user-content row, column count matching the source row; `insert` (fallback) formats a single section per container kind.
- `InteractionPopupMenu`: item count matches the passed array; empty array shows "No relevant sections found".
- Toggle: `WritingAssistMatrix.applies(.interaction, to: .spelling)` returns `false`; all five content languages return `true`.
- `AppState.isInteractionAvailable` reflects coordinator's `isAvailable` after `updateDetection`.

## Risks and Constraints

| Risk | Mitigation |
|---|---|
| **Detection false positives** — regex matches a `\|` character that isn't a table | `markdownTableRow` requires ≥2 `\|` on the same line and at least one adjacent line also having `\|`; isolated `\|` characters don't trigger |
| **Hiding More-Context unexpectedly** — precedence could suppress More-Context where the user wanted a word lookup | Precedence fires only when a *structural* special element is detected; single-word selections in prose never match a syntax term, so More-Context still appears. Disabling a language's Interaction toggle restores More-Context for that mode |
| **Registry drift** — `special_elements.json` references a topic/lookup that doesn't exist | Tolerant decode skips bad entries; a resource slot whose lookup returns nothing is omitted from the template (the row simply doesn't appear) rather than inserting an empty/garbage row |
| **Fuzzy mis-ranking (fallback only)** — heading match surfaces an irrelevant section | Registered elements never use fuzzy; for the fallback, a score floor drops weak matches (empty popup, not a wrong section); covered by the fallback ranking test |
| **HTML/ASCII have no body sub-headings** | Fallback `ResourceSectionIndex` uses topic title + `searchTerms` for those resources; registered HTML/ASCII elements use explicit `*Topic` lookups, so neither depends on body headings |
| **Semantic-search temptation** | `LocalSemanticSearch` (NLEmbedding) loads a ~300 MB model — rejected for an inline popup (SR-3/SR-4); lightweight deterministic `HeadingFuzzyMatcher` used instead |
| **HTML detection in WKWebView** — no `NSRange` for DOM position | Use the JS `selectionchange` captured text (already in place); detection is text-pattern only, not DOM-dependent |
| **SR-1: module 9 must not import module 3** | `ContentInserter` returns `(newText, insertionRange)`; the caller (module 3) does the `NSTextView` write |
| **Undo safety** | `NSTextView.insertText(_:replacementRange:)` is undo-registered automatically; no direct string mutation |
| **Resource index empty** | `InteractionProvider` returns empty `InteractionResult.sections`; popup shows "No relevant sections found" — no crash |
| **Performance** | Detection is synchronous regex on the visible range only (not the full file); heading extraction is cached per language; provider lookup is async on the actor thread |

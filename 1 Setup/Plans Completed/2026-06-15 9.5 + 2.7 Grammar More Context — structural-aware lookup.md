## Purpose
Make the grammar "More Context" lookup selection-aware: detect where the selection starts and finishes, and for multi-word selections prioritise structural grammar topics over lexical ones (falling back to lexical when no structural topic matches).

## Success Condition
- Selecting a single word (e.g. "their") still resolves to its lexical topic (Their / There / They're) exactly as today.
- Selecting a multi-word phrase that spans a subject or object (e.g. "the tired old dog") resolves to a structural topic (Subject & Predicate / Phrase Types / Clause Types / Direct & Indirect Objects) ahead of any lexical match.
- A multi-word selection whose only matches are lexical (no structural topic scores) still resolves to the best lexical topic — no empty result.
- New Swift Testing cases in `9 Resources/Tests/` cover: single-word → lexical; multi-word subject → structural; multi-word object → structural; multi-word lexical-only → lexical fallback; the role detector's subject-vs-object verdict on a known sentence.
- Existing grammar lookup tests and all three host call sites (editor, Markdown preview, HTML preview) still compile and pass.

## Steps

1. **Add `structuralLevel` to the topic model**
   What: Add a `structuralLevel` field to `GrammarHelpContent` (an enum: `.structural` / `.lexical`, `Codable`, defaulting to `.lexical` when absent so decode never fails on older data). Define the enum in its own file per SR-6.
   Why: The user chose explicit per-topic tagging over deriving from `category`; this is the field the new scoring reads. A defaulted decode keeps the index forward/backward compatible (SR-2).

2. **Tag all 75 topics in `grammar_help_index.json`**
   What: Add `"structuralLevel"` to every topic. Structural: all 6 `sentence-structure` topics plus the structural `grammar` topics (Subject-Verb Agreement, Dangling/Misplaced Modifiers, Conjunctions, Prepositions, Articles) and `punctuation`. Lexical: `spelling`, `usage`, word-level `style`, and the remaining `edge-cases`/`grammar` word topics. Record the exact mapping in the plan's notes as it is applied.
   Why: Scoring needs a real structural/lexical signal on each topic. Doing it once in data keeps the algorithm simple and tunable per-topic.

3. **Extend `HelpContextQuery` with selection extent (Foundation)**
   What: Add `selectionLength: Int` (default `0`) to `HelpContextQuery` in `2 Foundation/2.7 Utilities/HelpContextResolving.swift`, alongside the existing `cursorOffset` (selection start). Keep it `Sendable` and the initializer source-compatible via the default.
   Why: "Where the selection finishes" is unknowable today (ISS-135). Foundation owns the query primitive (SR-1); a defaulted field means no existing caller breaks.

4. **Thread selection length through `MoreContextMenu` (Foundation)**
   What: Add an optional `selectionLength: Int = 0` parameter to `MoreContextMenu.items(...)` and pass it into the `HelpContextQuery` it builds.
   Why: The builder is the single seam every host uses; an optional parameter keeps the Markdown and HTML call sites compiling unchanged while letting the editor supply a real length.

5. **Populate selection length at the editor call site**
   What: In `EditorTextView.swift` (~line 301), pass `selectionLength: selection.length` to `MoreContextMenu.items(...)`. Optionally do the same in `MarkdownPreviewCoordinator.swift` using `selectedRange.length`. Leave `HTMLPreviewView.swift` at the default `0` (WKWebView selection has no reliable offset).
   Why: The editor is the primary grammar surface and already holds the full `NSRange`; this is where multi-word detection matters most.

6. **Build the selection role detector (Resources, new file)**
   What: Add a `GrammarSelectionAnalyzer` (own file, SR-6) that takes `fullText`, `cursorOffset`, and `selectionLength` and returns a small value type: word count of the selection, and an approximate role (`.subject` / `.object` / `.unknown`). Use `NaturalLanguage` `NLTagger` with `.lexicalClass` to find the sentence's main verb, then classify the selected span by position relative to it (noun phrase before main verb ≈ subject, after ≈ object). Run on a `Task` off the main thread; the type is `Sendable`.
   Why: The user chose the NaturalLanguage positional heuristic. Apple gives POS tags but not true dependency roles, so this is an explicit approximation isolated in one testable type (SR-5, SR-4).

7. **Add structural-aware scoring to `GrammarHelpIndex`**
   What: Add a new method (e.g. `searchByTerm(_:preferStructural:)`) that reuses the existing scoring but, when `preferStructural` is true, adds a weight to `.structural` topics so they sort above lexical ones. Leave the original `searchByTerm(_:)` untouched for callers that don't need bias.
   Why: Keeps the single-word path byte-for-byte unchanged while giving the multi-word path a structural preference; falling out of the same scored list guarantees lexical fallback when no structural topic scores (SR-2).

8. **Wire role + length into the lookup coordinator**
   What: Extend `GrammarHelpCoordinator.lookup` to accept the analyzer result (word count + role), and call the structural-biased search when the selection is multi-word (or role is subject/object). Single-word selections keep calling the original path. Preserve the `primaryTopic` + `alternatives` shape.
   Why: The coordinator is the orchestration point; routing here keeps the resolver thin and the See-also behaviour intact.

9. **Update the resolver's `.grammar` branch to stop discarding context**
   What: In `SputnikHelpContextResolver.resolve`, build the `GrammarSelectionAnalyzer` result from `query.fullText` / `query.cursorOffset` / `query.selectionLength` and pass it into the coordinator lookup. Other `kind` branches are unchanged.
   Why: This is the exact line (ISS-135) that throws away `fullText`/offset today; feeding it the analysis is what activates the whole feature (SR-1: module 9 owns this orchestration).

10. **Write Swift Testing coverage**
    What: Add tests under `9 Resources/Tests/` for the five Success-Condition scenarios plus direct unit tests of `GrammarSelectionAnalyzer` (subject vs object on a known active-voice sentence, word-count detection) and the structural-biased scoring. Note in a comment that passive-voice role detection is a known heuristic limitation, not a test failure.
    Why: Locks the behaviour and documents the heuristic's boundary so future edits don't silently regress it.

11. **Update Module Guides 9.5 and 2.7**
    What: In `9.5 Grammar Help/guide.md`, document the structural/lexical tagging, the analyzer, and the multi-word prioritisation; replace the `<!-- assumed -->` `GrammarHelpContent` description with the real shape including `structuralLevel`. In `2.7 Utilities/guide.md`, add `selectionLength` to the `HelpContextQuery` description and the `MoreContextMenu.items` signature. Bump `last_updated`/`last_verified` to today.
    Why: SR-1 and the working conventions require the guides to match the code after a change; both guides currently describe the pre-feature shape.

## Risks and Constraints
- **Heuristic accuracy (SR-5 limit):** NaturalLanguage gives POS, not dependency roles. Passive voice, inversions, and fronted objects will misclassify subject/object. Accepted by design; isolated in `GrammarSelectionAnalyzer` and noted in tests/guide.
- **Cross-module change (SR-1):** Steps 3–4 touch Foundation 2.7, which every host imports. Mitigated by making both additions defaulted/optional so no existing caller breaks — but Foundation changes must be flagged (they are, here).
- **Index data integrity (SR-2):** Hand-tagging 75 topics risks a typo. The defaulted `structuralLevel` decode means a missing/misspelled value degrades to `.lexical` rather than crashing; a test asserts every topic decodes.
- **Threading (SR-4):** NLTagger work must not run on the main thread; the analyzer runs inside the resolver's existing `Task`.
- **No new dependencies (SR-5):** `NaturalLanguage` is an Apple framework — compliant.

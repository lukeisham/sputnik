## Purpose
Make `SyntaxHighlighter`'s range-based re-highlight actually work — currently `editedRange` is always `nil` (dead code), `baseOffset` is silently ignored (a latent mis-coloring bug), and the code-block cache is never invalidated (a latent stale-cache bug) — so re-highlighting is correct today only by accident (because the full-document path is always taken).

## Success Condition
- Typing in a large (multi-thousand-line) Markdown/HTML/JSON document only re-colors the edited region plus its look-behind margin — verified by instrumenting or logging the range actually passed to `highlight(mode:editedRange:)` during a real edit, confirming it's non-nil and scoped, not the full document.
- Editing text *above* a fenced ```html code block correctly invalidates and re-computes that block's cached HTML attributes on the next highlight pass — no stale/wrongly-offset coloring inside the code block after an edit above it.
- Typing inside a large document does not visibly lag or drop frames on ordinary hardware (informal manual check, or a timed test if the harness supports it) — confirming the O(n)-per-keystroke regression is actually gone, not just theoretically fixed.
- All existing `TextEditorModuleTests` and `SyntaxHighlighterCodeBlockTests` pass; new tests cover the range-scoping and cache-invalidation behavior specifically.

## Steps

- [ ] 1. **Get the real edited range from `NSTextView`/`NSTextStorage`, not the notification's userInfo**
   What: In `EditorView.Coordinator`, capture the edited range via `NSTextStorageDelegate`'s `textStorage(_:didProcessEditing:range:changeInLength:)` (implemented on the coordinator, wired as the `NSTextStorage`'s delegate) instead of trying to read a nonexistent key from `NSText.didChangeNotification`'s `userInfo`. Store the most recent edited range on the coordinator and pass it into `textDidChange`'s highlight-scheduling call.
   Why: ISS-201 — `NSText.didChangeNotification` never carries an `"NSRange"` key; `NSTextStorageDelegate` is the actual AppKit-supported way to learn what changed and by how much.

- [ ] 2. **Apply `baseOffset` in `SyntaxHighlighter.buildAttributes`**
   What: In `buildAttributes(for:text:baseOffset:)`, after computing attribute ranges relative to the passed-in `text` segment, add `baseOffset` to each returned range's `location` before returning — for every mode branch (`markdownAttributes`, `htmlAttributes`, `jsonAttributes`), not just at the call site.
   Why: ISS-201 — without this, a non-nil `editedRange` (which step 1 now actually supplies) would apply segment-relative colors at document-relative positions, mis-coloring the document. This must land together with step 1, not before it, since step 1 is what makes this code path reachable for the first time.

- [ ] 3. **Invalidate `codeBlockCache` entries that overlap an edit**
   What: In `SyntaxHighlighter.highlight(mode:editedRange:)`, before running `markdownAttributes` (which reads `codeBlockCache`), remove cache entries whose fenced-block range overlaps or falls after the edited range (an edit above a cached block shifts everything below it, invalidating both the block's own content and its cached location key). The simplest correct approach: since fenced-block boundaries can move on any edit above them, clear the entire `codeBlockCache` on any edit whose range starts before the highest-known cached block location, or — more precisely — recompute `fencedCodeBlocks(in:)` fresh each pass (already happens) and only reuse a cache entry when its block's *content* is verified unchanged (e.g. hash the block content, not just its location, as the cache key).
   Why: ISS-201 — the current cache is write-only; nothing ever removes or refreshes an entry, so cached HTML-in-code-block attributes silently go stale (wrong document offsets, or colors computed from now-stale content) the moment any edit shifts a block's position.

- [ ] 4. **Re-verify the look-behind margin still catches multi-line constructs with real (non-full-document) ranges**
   What: With `editedRange` now genuinely scoped (steps 1–2), confirm `expandedRange(for:in:)`'s 5-line look-behind margin is still sufficient for the module's actual constructs (fenced code blocks can be longer than 5 lines from their opening delimiter to an edit deep inside them) — decide whether the look-behind needs to search backward for the nearest fence marker specifically, rather than a fixed line count, given this is now load-bearing instead of dead code.
   Why: Previously this logic was never exercised with a real edited range (since `editedRange` was always `nil`), so its correctness was never actually tested in practice — worth a fresh look now that it will run on every keystroke.

- [ ] 5. **Add/extend unit tests**
   What: In `Tests/SyntaxHighlighterCodeBlockTests.swift` and `TextEditorModuleTests.swift`: (a) feed a document, call `highlight(mode:editedRange:)` with a small mid-document range, assert only attributes within (range + margin) are touched, not the full document; (b) place a fenced HTML code block, edit text above it, re-highlight, assert the code block's cached attributes are recomputed at correct offsets (not stale); (c) a large-document performance-shape test if the harness supports timing assertions (even a loose upper bound) to catch a regression back to O(n).
   Why: This is exactly the kind of "worked by accident because the buggy path was unreachable" bug that needs explicit regression coverage once made reachable — otherwise a future refactor could silently reintroduce the same three bugs.

- [ ] 6. **Manual verification pass**
   What: Run the app; open a large Markdown file with a fenced ```html code block partway through, edit text well above the block, confirm the block's HTML coloring stays correct; type continuously in a large document and watch for any highlighting lag or visible full-document re-color flash.
   Why: Range-scoped highlighting correctness and responsiveness are best confirmed by direct observation, since the bug class here is specifically about *what actually gets re-colored* — hard to fully verify with tests alone against real AppKit layout behavior.

## Risks and Constraints
- This is the trickiest plan of the module 3.1 batch — three interacting bugs (dead range extraction, ignored offset, no cache invalidation) all currently masked by the same root cause (range is always nil, so full-document re-highlight is always "correct" by brute force). Land steps 1–3 together in one commit/PR rather than incrementally, since step 1 alone (without steps 2–3) would activate the offset bug and the stale-cache bug in production.
- SW-1: `NSTextStorageDelegate` callbacks must stay `@MainActor`-safe; verify the delegate assignment doesn't conflict with any existing `NSTextStorage` delegate usage elsewhere in the module.
- SR-4: the entire point of this plan is restoring the O(range) guarantee — verify with the performance-shape test in step 5, not just "it looks fine."
- Do not change the *visual* highlighting rules (regex patterns, colors) — this plan is scoped to fixing the range-scoping mechanism, not the highlighting content itself.

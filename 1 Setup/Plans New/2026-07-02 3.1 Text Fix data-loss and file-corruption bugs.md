## Purpose
Stop the editor from silently discarding unsaved edits on external file changes and from silently corrupting non-ASCII files through a bad encoding probe, plus close the two smaller suppression/logging gaps in the same file-watching path.

## Success Condition
- Edit a file in Sputnik without saving, then modify the same file externally (e.g. `echo x >> file.txt` in the integrated terminal) → the user is prompted to choose between keeping their edits and reloading the external version, never silently overwritten.
- Open a UTF-8 file crafted so a multi-byte character straddles the 8192-byte probe boundary → it loads correctly (not as Latin-1 mojibake), and saving it back produces byte-identical UTF-8 output (round-trip test).
- Point `EncodingGuard` at a file that is genuinely undecodable in any candidate encoding → it still throws `Failure.binaryOrUnreadable`, confirming the reachability fix didn't remove the safety net.
- Force `open(O_EVTONLY)` to fail (e.g. permission-denied path in a test) → a log entry is emitted via `SputnikLogger.editor`; the watcher's failure state is inspectable/testable rather than silent.
- Force `save()`'s write to throw after `suppressOnce()` has already been called → the suppression credit is restored (or the credit accounting is otherwise correct) so the next real external change is still detected.
- All existing `TextEditorModuleTests` pass; new tests cover each fix.

## Steps

- [ ] 1. **Gate external reload on dirty state**
   What: In `EditorViewModel.startWatchingFile`'s `onChanged` closure, before calling `openDocument(url)`, check `isDirty`. If clean, reload as today. If dirty, present a conflict prompt (reuse the `NSAlert` pattern already used for `promptFileDeleted`/`promptReloadFailed`) offering "Keep My Changes" (do nothing, leave the buffer as-is, optionally note the file changed externally) vs. "Reload from Disk" (discard local edits and call `openDocument(url)`).
   Why: ISS-199 — external file changes are common in Sputnik's core workflow (editing while running terminal commands against the same file), and today they silently destroy unsaved work with zero recovery path (the crash-recovery cache would still have it, but the user isn't told).

- [ ] 2. **Fix the encoding probe's boundary truncation**
   What: In `EncodingGuard.validate`, before attempting to decode the 8 KB probe as UTF-8, trim trailing bytes that form an incomplete UTF-8 sequence at the probe's end (reuse or adapt the same trailing-incomplete-sequence logic already proven in the Terminal module's `IncrementalLineDecoder.incompleteTrailingByteCount`, or write a small local equivalent) before the `String(data:encoding:)` attempt for `.utf8` specifically.
   Why: ISS-200 — a split multi-byte character at the probe boundary currently causes `.utf8` decode to fail and falls through to `.isoLatin1`, which never fails — every affected file loads as mojibake with no error shown.

- [ ] 3. **Preserve (or re-verify) encoding through save**
   What: In `EditorViewModel`, store the `String.Encoding` detected by `EncodingGuard.validate` at load time (e.g. a new `loadedEncoding: String.Encoding` property, defaulting to `.utf8` for untitled/new documents) and use it — or explicitly re-encode to UTF-8 as an intentional normalization, documented as such — in `save()`'s write instead of hardcoding `.utf8` silently. Decide and document which behavior is intended: preserve the original encoding, or normalize to UTF-8 (acceptable if explicit and only after step 2 guarantees correct *detection*, so a Latin-1 file is only normalized if it's genuinely Latin-1, not misdetected UTF-8).
   Why: ISS-200 — today, a misdetected load (before step 2's fix) plus an always-UTF-8 save is what makes the corruption *permanent* on the next save; even after step 2, silently writing UTF-8 for a genuinely non-UTF-8 source file is a real design decision that shouldn't be implicit.

- [ ] 4. **Fix the encoding candidate ordering / unreachable-throw issue**
   What: Either reorder `EncodingGuard`'s candidate list so `.isoLatin1` (which never fails to decode) is tried last, immediately before falling through to the `binaryOrUnreadable` throw — making it an explicit last-resort fallback rather than a silent catch-all ahead of `.windowsCP1252` — or replace the blanket "any byte sequence decodes as Latin-1" acceptance with a more meaningful heuristic (e.g. only accept Latin-1 if a reasonable fraction of bytes are printable ASCII/Latin-1-range, otherwise prefer throwing `binaryOrUnreadable`).
   Why: ISS-200 — `.windowsCP1252` is currently unreachable in the candidate loop, and the final `throw` is effectively dead code; this makes the guard's actual behavior match its documented "reject binary/unreadable" intent.

- [ ] 5. **Log and expose FileWatcher init failure**
   What: In `FileWatcher.init`, when `fd < 0`, log via `SputnikLogger.editor` (or the appropriate channel) with the `errno`/path, and add a small public flag (e.g. `public private(set) var isActive: Bool`) so `EditorViewModel.startWatchingFile` can check it and optionally surface a non-blocking notice (or at minimum, so this is testable).
   Why: ISS-206 — a silently-inert watcher means external-change detection just doesn't work for that document, with nothing in logs or UI to explain why if a user reports "the reload prompt never showed up."

- [ ] 6. **Fix the suppression-credit leak on save failure**
   What: In `EditorViewModel.save()`, move `fileWatcher?.suppressOnce()` to immediately before the actual write call (already close to correct), and on write failure (the `Task.detached` throwing), call a new `fileWatcher?.unsuppressOnce()` (decrement the credit back) or restructure so the credit is only consumed after a confirmed-successful write.
   Why: ISS-207 — a failed save currently leaves a stale suppression credit that silently eats the next real external-change notification, compounding with ISS-199's fix (the dirty-check conflict prompt would then never fire for that one change).

- [ ] 7. **Add/extend unit tests**
   What: In `Tests/TextEditorModuleTests.swift`: (a) `EncodingGuard` test with a crafted file whose UTF-8 multi-byte sequence straddles the 8 KB boundary, assert `.utf8` is still detected; (b) a genuinely-undecodable binary file still throws `binaryOrUnreadable` after the reordering fix; (c) a dirty-buffer + external-change scenario against a testable seam (may require extracting the conflict-decision logic from the `NSAlert`-coupled code into a pure function that the view model calls, if not already separable) confirming the reload path is *not* taken automatically when dirty; (d) `FileWatcher` failure-path test confirming `isActive == false` and a log line when given an unopenable path.
   Why: These are exactly the input-shape edge cases (boundary-straddling UTF-8, failed opens, save-then-external-change races) that don't show up in casual manual testing.

- [ ] 8. **Manual verification pass**
   What: Run the app; reproduce the dirty-buffer-plus-external-write scenario via the integrated terminal (`echo >> currently-open-file.txt`), confirm the prompt appears and both choices work correctly; open a real-world UTF-8 file with non-ASCII content near typical file-size boundaries if one is available.
   Why: The conflict-prompt UX and encoding round-trip are best confirmed hands-on per CLAUDE.md's golden-path testing guidance.

## Risks and Constraints
- SR-2: no force-unwraps introduced; the conflict-prompt path must never silently pick a side — always require explicit user action when data could be lost.
- SW-1: keep all `NSAlert` presentation on `@MainActor`, matching the existing `promptFileDeleted`/`promptReloadFailed` pattern.
- Step 3's encoding-preservation decision affects every subsequent save of every open document — get sign-off on preserve-vs-normalize behavior before implementing, since it's a user-visible product decision, not just a bug fix.
- Coordinate with any in-flight recovery/crash-cache behavior: a "Keep My Changes" choice in step 1 should not clear the crash-recovery cache (the buffer is still dirty relative to disk).

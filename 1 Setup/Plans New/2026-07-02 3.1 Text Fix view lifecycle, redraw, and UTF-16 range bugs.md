## Purpose
Clean up the editor's teardown leak, an over-broad redraw that contradicts its own comment, three latent Character-vs-UTF-16-range mismatches (ghost text, window-restore caret, search highlighting), and one redundant per-render font/background reset.

## Success Condition
- Closing/dismantling an editor column releases the `NSTextView`/`NSTextStorage` — `viewModel.textView`, `.scrollView`, and `.searchController` are `nil` afterward, and stale-view consumers (ASCII Studio insert, minimap) correctly no-op instead of touching a dead view.
- Moving the caret with arrow keys in a large document does not trigger a full-view redraw (including the indent-guide pass) — only the old and new current-line rects are invalidated.
- A ghost-text suggestion containing a non-BMP character (e.g. an emoji in a completion string, if reachable) accepts/clears at the correct text position with no residue or adjacent-character deletion. If no current provider emits non-BMP suggestions, a synthetic test still proves the range math is correct.
- Pressing Next/Previous in the Find bar visually moves the "current match" highlight to the newly-selected match, not just the caret.
- Restoring window state (caret + scroll) on a document containing non-BMP characters places the caret at the correct position, not silently clamped wrong.
- Toggling an unrelated setting (e.g. current-line highlight) does not also reset the font/typing attributes as a side effect; font/background changes still apply correctly when the actual font/background setting changes.
- All existing `TextEditorModuleTests` pass; new tests cover each fix where testable without a live window.

## Steps

- [ ] 1. **Clear strong view references on teardown**
   What: In `EditorView.dismantleNSView(_:coordinator:)`, in addition to removing the scroll observer, clear `coordinator`'s references and — since `viewModel` is accessible via `coordinator` — set `viewModel.textView = nil`, `viewModel.scrollView = nil`, `viewModel.searchController = nil`. Confirm `EditorViewModel`'s properties are declared in a way that allows this (they're currently `public var`, not `private(set)`, so this is straightforward) and audit any consumer that reads these properties for correct nil-handling (ASCII Studio's `activeTextView`/`lastKnownTextView` fallback, the minimap binder in `TextEditorPanel`'s `onDisappear`, `flushViewState`).
   Why: ISS-202 — today these strong references outlive the dismantled `NSTextView`, keeping the full text storage (up to 10 MB) alive and letting stale consumers silently operate on a dead view instead of failing gracefully.

- [ ] 2. **Fix the over-broad selection-change redraw**
   What: In `EditorView.Coordinator.textViewDidChangeSelection`, remove the unconditional `tv.needsDisplay = true` and instead invalidate only the old highlighted-line rect (`setNeedsDisplay(oldRect, avoidAdditionalLayout: true)`) and the new current-line rect (compute it the same way `drawBackground(in:)` does, or trigger the view to recompute and invalidate just that rect).
   Why: ISS-203 — the doc comment already describes the intended targeted-invalidation behavior; the implementation just doesn't do it. Every cursor movement currently pays a full-view redraw including the indent-guide pass, which is real per-keystroke/per-arrow-key cost in a large document (SR-4).

- [ ] 3. **Fix `GhostTextOverlay`'s Character-vs-UTF-16 range mismatch**
   What: In `GhostTextOverlay.show`, compute `suggestionLength` from `(suggestion as NSString).length` (UTF-16 code units) instead of `suggestion.count` (grapheme clusters), matching how `NSRange` is actually interpreted everywhere else in the type (`accept()`, `clear()`).
   Why: ISS-204 — a ghost suggestion containing any non-BMP scalar currently computes wrong `NSRange`s in `accept()`/`clear()`, which can leave ghost-text residue as real text or delete adjacent real user characters — corruption-adjacent even if today's providers don't emit non-BMP suggestions.

- [ ] 4. **Exclude the ghost-text range from syntax-highlight color writes**
   What: In `SyntaxHighlighter.highlight`, before writing `.foregroundColor` attributes back to `NSTextStorage`, skip (or re-apply after) any subrange currently tagged with `GhostTextOverlay.ghostAttributeKey` — the highlighter needs a way to query this from the storage's existing attributes (`storage.attribute(GhostTextOverlay.ghostAttributeKey, at:effectiveRange:)`) rather than needing a new coupling between the two types.
   Why: ISS-204 — the debounced highlight pass currently overwrites the ghost text's grey color with normal syntax colors ~0.3s after it appears, before the user has accepted or dismissed it, which is visually confusing (looks like real text momentarily).

- [ ] 5. **Fix search-highlight staleness on next/previous navigation**
   What: In `SearchController.nextMatch()`/`previousMatch()`, call `applyHighlights()` (not just `scrollToCurrentMatch()`) after updating `currentMatchIndex`, so the current-vs-other-matches color distinction moves with the selection.
   Why: ISS-205 — the "current match" highlight visually staying on the previous match while the actual selection jumps elsewhere is a straightforward, easily user-visible correctness bug in a frequently-used feature (Find/Replace).

- [ ] 6. **Refresh match ranges before replace, or explicitly document the staleness window**
   What: In `SearchController.replaceCurrent()`, either re-run `search()` immediately before reading `matchRanges[currentMatchIndex]` if the document may have changed since the last search (cheap for typical document sizes; the existing `search()` already does a full re-scan), or, if re-searching on every replace is deemed too expensive, add a comment explaining why the existing bounds-only guard is considered sufficient and under what conditions staleness is actually reachable.
   Why: ISS-205 — the current bounds check only prevents an out-of-range crash, not a replace at a since-shifted (wrong) location; worth resolving explicitly rather than leaving ambiguous.

- [ ] 7. **Fix `applyViewState`'s Character-vs-UTF-16 clamp**
   What: In `EditorViewModel.applyViewState`, replace `textView.string.count` with `(textView.string as NSString).length` for both the `clampedLocation` and `clampedLength` calculations.
   Why: ISS-208 — `NSRange`/`selectedRange()` operate in UTF-16 code units; clamping against a `Character` count under-clamps for any document containing non-BMP scalars, producing an invalid or mis-positioned restored caret.

- [ ] 8. **Gate the font/background reapplication on an actual change**
   What: In `EditorView.updateNSView`, before calling `applyFontAndBackground(textView, settings: settings)` unconditionally, compare the resolved font/background against what's currently applied (cache the last-applied values on the `Coordinator`, similar to `lastAppliedLoadToken`) and only reapply when they differ.
   Why: ISS-209 — resetting font/background/typing attributes on every SwiftUI re-render (which can happen for reasons unrelated to font settings) is wasted work and a candidate for subtle typing-attribute glitches during active typing.

- [ ] 9. **Add/extend unit tests**
   What: In `Tests/TextEditorModuleTests.swift`: (a) a `GhostTextOverlay` test with a synthetic non-BMP suggestion string, assert `accept()`/`clear()` compute correct UTF-16-based ranges; (b) `applyViewState` test with a non-BMP-containing document, assert correct clamp; (c) `SearchController` test confirming `nextMatch()` updates highlight state (may need to inspect `NSTextStorage` attributes directly); (d) a teardown test if feasible confirming `EditorViewModel`'s view references become nil after `dismantleNSView`.
   Why: The UTF-16/Character mismatches (b, and ideally a) are exactly the class of bug invisible in ASCII-only manual testing — deserve explicit non-BMP test fixtures now that they're identified.

- [ ] 10. **Manual verification pass**
   What: Run the app; close an editor column and confirm no dangling references via a memory graph/Instruments check if convenient; move the caret around a large document and watch for redraw flicker; exercise Find/Replace next/previous and confirm highlight tracking; if any ghost-text provider can be coaxed into a non-ASCII suggestion, test that path too.
   Why: Redraw behavior and view lifecycle are best confirmed by direct observation/profiling, not just unit tests against isolated logic.

## Risks and Constraints
- SW-2: step 1's teardown fix must not itself introduce a crash — every consumer of `viewModel.textView`/`.scrollView`/`.searchController` needs an audited nil-safe path (most already use `guard let` per SR-2, but confirm ASCII Studio's `activeTextView()` and the minimap binder specifically).
- SR-4: steps 2 and 8 are both "stop doing unnecessary work" fixes — verify with before/after observation that the targeted invalidation in step 2 actually looks correct (no missed redraw regions causing visual artifacts from the old full-redraw safety net being removed).
- This plan groups several independent, low-interdependency fixes — they can land in any order or be split further if preferred, but are batched here because they're all small, mechanical, and touch the same handful of files.
- Do not fold in the range-based-syntax-highlighting rework (companion plan) — file overlap in `EditorView.swift`/`SyntaxHighlighter.swift` exists (step 4 here touches `SyntaxHighlighter.highlight`), so land whichever plan is ready first and rebase the other, or land them in the same PR if that's simpler given the overlap.

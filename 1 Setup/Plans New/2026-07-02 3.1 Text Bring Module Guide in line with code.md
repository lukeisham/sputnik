## Purpose
Correct the four drift points in the 3.1 Text Module Guide — the outdated deinit-safety description, the missing `.json` mode, the duplicated/missing Source Files entries, and the false range-based re-highlighting claim — so the guide is trustworthy again as the module's source of truth.

## Success Condition
- The guide's Invariants section describes the *actual* current deinit mechanism (`@MainActor deinit` calling isolated private methods directly), not the superseded `nonisolated`/`nonisolated(unsafe)` pattern from ISS-082.
- The guide's mode diagram, Source Files table, and State Owned list all include `EditorMode.json` / `jsonModeActive` / `jsonValidationErrors`, consistent with how `.markdown`/`.html`/`.asciiArt` are already documented.
- The Source Files table lists `EditorTextView.swift` once (not twice) and adds entries for `EditorTerminalBridge.swift`, `ExtractiveSummarizer.swift`, `ImageDropMarkupBuilder.swift`, and `SummaryPopoverContent.swift`.
- The Threading Model / Invariants text about range-based re-highlighting either (a) accurately reflects the fixed behavior, if the companion "Fix range-based syntax highlighting" plan has already landed, or (b) is corrected to state the current actual behavior (full re-highlight on every debounced change) with a forward note that range-scoping is tracked as ISS-201, if this guide plan lands first.
- `last_updated` and `last_verified` are bumped to this plan's completion date; `status` remains `active` given the volume of still-open companion-plan work in this module.

## Steps

- [ ] 1. **Re-verify the deinit mechanism against current code**
   What: Read `EditorViewModel.swift`'s `deinit` (currently `@MainActor deinit { stopWatchingFile(); stopRecoveryWrite(); resignUserActivity() }`, with the three properties as plain `private var`, not `nonisolated(unsafe)`) and rewrite the guide's corresponding Invariants bullet to describe this directly, removing the now-inaccurate ISS-082-era description of `nonisolated` helper methods.
   Why: ISS-210(1) — the guide currently documents a mechanism (`nonisolated` methods + `nonisolated(unsafe)` properties) that has been superseded by a simpler `@MainActor deinit`, which is worth noting as an improvement, not an error, but the guide must describe what's actually there.

- [ ] 2. **Add `.json` mode throughout the guide**
   What: Add `.json` to the mode diagram's mode-list (alongside `.plainText`/`.markdown`/`.html`/`.asciiArt`), describing that it activates 3.6 JSON suggestions/validation; add `jsonModeActive` and `jsonValidationErrors` to the State Owned list and to `EditorViewModel`'s Key Types bullet, matching the existing style used for `htmlModeActive`/`spellCheckActive`.
   Why: ISS-210(2) — `EditorMode.json` and its gating state are fully implemented in code (confirmed in `EditorMode.swift`, `EditorViewModel.swift`) but entirely absent from the guide, which currently only documents three of the four (soon five, with plaintext) modes.

- [ ] 3. **Fix the Source Files table**
   What: Remove the duplicate `EditorTextView.swift` row (keep the fuller of the two existing descriptions, merging any detail from the shorter one); add rows for `EditorTerminalBridge.swift` (terminal-integration commands: send selection, run file, insert terminal output — read the actual file to write an accurate one-line description), `ExtractiveSummarizer.swift` (on-device TF-scored summarization used by "Summarize Locally"), `ImageDropMarkupBuilder.swift` (builds Markdown/HTML image markup for drag-and-drop image inserts), and `SummaryPopoverContent.swift` (SwiftUI content view for the summary popover).
   Why: ISS-210(3) — these four files exist and are wired into the module (confirmed via the source listing and `EditorTextView`'s usage of `ExtractiveSummarizer`/`SummaryPopoverContent`, and `EditorViewModel`'s terminal-bridge methods) but have no guide entry at all, making the Source Files table an incomplete map of the module.

- [ ] 4. **Correct or forward-reference the range-based re-highlighting claim**
   What: Check whether the companion "Fix range-based syntax highlighting" plan (ISS-201) has landed. If yes, verify the guide's existing claim now matches reality and leave it (or tighten the wording based on the actual final implementation). If not yet landed, edit the Threading Model bullet and the Invariants bullet about `SyntaxHighlighter` to state plainly that re-highlighting currently runs on the full document on every debounced change (the range-based mechanism described was never actually wired up — `editedRange` is always `nil` in practice), with a note referencing ISS-201 as the tracked fix.
   Why: ISS-210(4) — the guide currently asserts a performance characteristic (O(range) instead of O(n)) that is not true in the running code; a guide should never claim a fixed invariant that the code doesn't actually deliver, since that's exactly the kind of false confidence that lets a bug like this hide for a long time.

- [ ] 5. **Sweep the rest of the guide for related staleness while here**
   What: While making the above edits, skim the Diagram, Data Flow, and Dependencies sections once more for anything else that's clearly inconsistent with the code read during this review (e.g. confirm the "Markdown preview always receives the raw text regardless of mode" claim still holds, confirm the Dependencies list's Foundation/ResourcesModule/SputnikShared references are current). Fix anything unambiguous; leave anything uncertain as-is rather than guessing.
   Why: A guide-alignment pass is a natural time to catch adjacent small drift, but this plan's primary scope is the four ISS-210 items — don't let this step balloon into a full rewrite.

- [ ] 6. **Bump metadata and finalize**
   What: Set `last_updated` and `last_verified` to this plan's completion date. Keep `status: active` — the module has several open companion-plan issues (ISS-199–209) that this documentation-only plan does not resolve.
   Why: Keeps the guide's own metadata honest about when it was last checked against reality.

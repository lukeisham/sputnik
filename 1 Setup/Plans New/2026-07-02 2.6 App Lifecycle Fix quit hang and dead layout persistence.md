## Purpose
Guarantee the app can always quit even if a PTY teardown wedges, and remove (or wire up) the layout-persistence path that currently round-trips unchanged bytes every session.

## Success Condition
- Simulate a PTY that never confirms termination (e.g. temporarily stub `killAllPTYs()` to hang) and confirm the app still quits within the timeout window instead of hanging indefinitely.
- Normal quit (all PTYs terminate promptly) is unaffected — no regression in existing termination behavior.
- Either: `layout.json` visibly changes across a session when the layout actually changes (if wired up), or: the dead `flushLayout`/`layoutState` path is removed and the app still builds, tests pass, and quit/relaunch still restores window state correctly (which lives in `windows.json`, not `layout.json`).

## Steps

- [ ] 1. **Decide: wire up layout persistence or remove it**
   What: Confirm with the user/CLAUDE.md intent whether `LayoutState`/`layout.json` is meant to track something beyond per-window descriptors (already covered by `WindowDescriptor`/`windows.json`). If no distinct runtime state exists, remove `layoutState`, `flushLayout`/`flushLayoutSync`, and `restore()` from `PersistenceService` and `FilePersistenceService`; otherwise identify the mutation site that should call `flushLayout` during the session.
   Why: ISS-153 — the path is currently write-only (loads once, writes back unchanged), so it either needs a real producer or should not exist per SR-1 (Foundation should not carry dead state paths).

- [ ] 2. **Add a bounded timeout to the quit sequence**
   What: In `AppDelegate.applicationShouldTerminate`, race `withTaskGroup` awaiting all `killAllPTYs()` calls against a fixed timeout (e.g. 3 seconds) using `Task.sleep` in a second task group member; call `NSApp.reply(toApplicationShouldTerminate: true)` as soon as either the PTYs finish or the timeout elapses, whichever comes first.
   Why: ISS-152 — an unconditional wait on `killAllPTYs()` means one wedged PTY blocks quit forever, violating the crash-proof rule (SR-2) that failure paths must be handled explicitly.

- [ ] 3. **Log a warning when the timeout path is taken**
   What: If the timeout fires before all PTYs report done, log via `SputnikLogger`/`ErrorReporting` that quit proceeded with N PTYs still terminating, so this is diagnosable if it happens in the field.
   Why: Silent timeout fallback would hide a real PTY-lifecycle bug (module 7); a log line preserves crash-proof behavior without losing visibility (SR-2).

- [ ] 4. **Update tests / stubs**
   What: Update `2 Foundation/Tests/FoundationModuleTests.swift` (and any `PersistenceService` test stubs in module 3 that implement `flushLayout`) to match whichever outcome step 1 lands on — either remove the stub method or add a test asserting the quit-timeout behavior with a mock `TerminalLifecycle` that never completes.
   Why: Keeps the protocol/tests in sync with the production implementation.

## Risks and Constraints
- Removing `flushLayout`/`LayoutState` from the `PersistenceService` protocol is a breaking API change for every conformer — search all modules for `PersistenceService` conformances (module 3's test stubs already found: `TextEditorModuleTests.swift`, `HTMLSyntaxCheckerTests.swift`, `JSONLanguageTests.swift`) before removing, and flag this explicitly since it touches Foundation (SR-1: cross-module changes need a plan first, which this is).
- The quit-timeout value (3s) must be short enough not to feel broken to the user but long enough not to kill PTYs that are legitimately mid-cleanup — pick a value and document the rationale at the call site (MR-4 concerns: SIGTERM→SIGKILL escalation in `TerminalLifecycle` should already resolve quickly; confirm with module 7's guide before finalizing the number).
- If layout persistence is kept and wired up, identify all layout mutation points without introducing a new state-sync bug between `AppState`/`WindowState` and `AppDelegate.layoutState`.

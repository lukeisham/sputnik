## Purpose
Make `ProcessMonitor`, `MainAIMonitor`, and `KeychainService` behave and document themselves correctly — accurate CPU sampling, a watcher that survives atomic file replacement, tasks that don't defeat `[weak self]`, correct actor/thread documentation, and true background sampling.

## Success Condition
- Status bar CPU% visibly tracks Sputnik's own activity (e.g. spikes during a large paste/render, drops at idle) rather than sitting near a constant value.
- Editing `~/.claude/stats.json` via a simulated atomic replace (`mv` a new temp file over it) is picked up by the file watcher without waiting for the 5s poll.
- `MainAIMonitor`'s `deinit` actually fires when the object is released (add a test or manual check with a scoped `weak var` capture).
- `swift build` succeeds for the Foundation package; `swift test` passes.
- `KeychainService`'s doc comment matches its real isolation.

## Steps

- [ ] 1. **Fix CPU sampling to measure the process, not the machine**
   What: Replace `ProcessMonitor.sampleCPU()`'s use of `host_cpu_load_info` with per-thread sampling via `task_threads` + `thread_info(THREAD_BASIC_INFO)` summed across all threads of the current task, matching what Activity Monitor reports for a single process.
   Why: ISS-149 — the current implementation reports a whole-machine, boot-lifetime average that has nothing to do with Sputnik's own resource usage, which defeats the purpose of the RAM/CPU status-bar indicator (SR-4).

- [ ] 2. **Move `ProcessMonitor` sampling truly off the main actor**
   What: Wrap the mach sampling calls in `Task.detached(priority: .background) { … }` (or a `nonisolated` sampling function invoked from within the loop) so `sampleRAM()`/`sampleCPU()` do not run on `@MainActor`; keep only the property writes on `MainActor.run`.
   Why: ISS-157 — `Task(priority:)` inside a `@MainActor` type inherits main-actor isolation regardless of priority; the sampling currently runs on the main thread every 2s despite being intended as background work (MR-3).

- [ ] 3. **Re-arm the stats.json file watcher on rename/delete**
   What: In `MainAIMonitor.startFileWatcher()`'s `setEventHandler`, detect `.rename`/`.delete` in `watcher.data` and, when present, cancel the current source, close the old fd, and call `startFileWatcher()` again to open a fresh fd on the new inode — in addition to reading the file.
   Why: ISS-151 — Claude Code's atomic write-temp-then-rename replaces the file's inode; the existing fd goes stale after the first replace and the watcher silently stops firing, leaving only the 5s poll (contrary to the project's `MR-2`/ISS-111b guidance to use `DispatchSource` correctly for this exact case).

- [ ] 4. **Stop the infinite-loop tasks from defeating `[weak self]`**
   What: In `MainAIMonitor.startProcessing()` and `startStatsPolling()`, move the `guard let self` re-check inside each loop iteration instead of once before the loop (mirror `ProcessMonitor.start()`'s pattern: `let self` per-iteration, not held across the whole `for await`/`while` body).
   Why: ISS-150 — as written, `self` is upgraded once and held strongly for the entire lifetime of the infinite loop, so the `[weak self]` annotation provides no actual protection and `deinit` can never run while the task is alive (SW-2).

- [ ] 5. **Correct `KeychainService`'s threading doc comment**
   What: Update the doc comment at the top of `KeychainService` to state that access is `@MainActor`-isolated (matching the actual declaration) and that `SecItem*` calls, while thread-safe at the OS level, run on the main actor here — remove the "call from any thread" claim.
   Why: ISS-156 — the current comment contradicts the `@MainActor` annotation on the same type and could mislead a future contributor into assuming safe access from background code (SW-4).

- [ ] 6. **Tighten the Main-AI session-boundary heuristic**
   What: In `MainAIMonitor.processLine`, only treat `"clear"`/`"exit"` as a session-boundary signal when it looks like a shell prompt echo (e.g. the line is exactly `"clear"`/`"exit"` **and** immediately follows a prompt-like context) — at minimum, gate it behind a simple check that the terminal is not mid-output (e.g. require the previous processed line to have been blank/prompt-like), or document the accepted false-positive rate if a more precise signal isn't practical within this module's scope.
   Why: ISS-159 — as written, any program output line that happens to equal "clear" or "exit" (e.g. `echo exit`, a catted file) incorrectly clears Main AI detection.

- [ ] 7. **Add/extend unit tests**
   What: Add tests to `2 Foundation/Tests/FoundationModuleTests.swift` covering: (a) the corrected CPU sampler returns a plausible process-scoped value structure (can't assert exact %, but can assert the API shape and that repeated calls don't crash), (b) `MainAIMonitor` deinitializes when released once its tasks use per-iteration weak self, (c) the tightened `processLine` heuristic on a few representative lines.
   Why: Locks in the fixes so future refactors don't silently reintroduce the retain cycle or the stale-fd bug.

## Risks and Constraints
- Per-thread CPU sampling via `task_threads`/`thread_info` must free the returned thread list with `vm_deallocate` to avoid a mach port/memory leak — audit carefully (SR-2, SR-3).
- The file-watcher re-arm must not create a tight cancel/re-open loop if the target file is deleted and never recreated; guard with a short backoff or leave the poll as a fallback if `startFileWatcher()` fails to find the parent directory.
- Touches Foundation (module 2) — `MainAIMonitor` and `ProcessMonitor` are consumed by `StatusBarView` (module 2.4) and `AppDelegate` (2.6); no public API signatures change, so no other module should need edits, but rebuild/test module 3 and 7 (terminal) since `MainAIMonitor` implements `TerminalAIOutputObserving` consumed by Terminal.
- Keep all Task priorities per MR-3's table (`.background` for this maintenance/monitoring work).
